# Flutter Harness
One active task per root Build session, one ordinary Git feature branch per task. Sequential tasks may share the same OpenCode conversation; only verified canonical delivery resets task budgets. CLI prefix: python3 .flutter-harness/bin/harness.py
Native SDK/CLI first, no Skills/MCP by default. Read relevant source only; for architecture/theme read .flutter-harness/PRODUCT.md; for material behavior or UI read BEHAVIOR.md or DESIGN.md in .flutter-harness/templates/product.
Run begin <feature-branch> once per new task from a clean checkout; never reuse a delivered branch for the next task. Merge prerequisite PRs first if the new task depends on them. Stop for owner sync if installed revision differs from integration. Preserve unrelated work. Use feature-first MVVM, Material 3, adaptive system theme.
For bugs, reproduce the original failure or establish a concrete source-level proof before changing code; verify the same scenario after repair. Model material invariants in types/APIs where useful; write focused tests for changed behavior, error/retry/persistence and state transitions. Preserve regression invariants, including overlapping operations. On failure run affected tests before the final canonical check. Run check on the final candidate; do not rerun unchanged successful checks.
For focused UI changes and new screens implement directly; user references are optional. Do not launch or capture baseline unless meaningful before/after comparison is needed. If needed, launch auto before edits, wait for actual content, inspect and capture original state explicitly. After implementation and check, launch auto when runtime visual acceptance is required; it selects and pins one working iOS → Android → Web target. Use --only for platform-specific work. Inspect relevant final states, light/dark and affected widths; no all-platform ritual. For material visual changes declare visual-plan.json in work with baseline omitted unless relevant; use capture or capture-plan and visual-evidence. Required changed interactions must be covered. Use e2e only for actual platform/critical risk or explicit request.
Default Luna Medium. One implementation agent, no workers. Optional sequential read-only architect/advisor only for difficult decisions; independent reviewer for risk or material UI, Medium focused and High broad/risky. Fix proven findings without weakening tests. If a finding needs reproduction, run its smallest relevant scenario; do not treat preferences or unsupported hypotheses as defects. One bounded adjudication for disputed findings; no automatic premium escalation.
Retain application-specific regression protection in the app. For a confirmed reusable Harness failure, run `harness.py lesson CODE` using its listed categories (same CLI prefix); no app text or logs are sent. Record only safe evidence in the existing task PR if useful. Do not report ordinary app failures, missing prerequisites or speculative gaps. Reporter failure never blocks delivery; do not retry it manually. Do not modify installed Harness or add a reflection session.
Use prepare-delivery --message "commit" --title "PR title" --body "summary" [--review] [--visual] [--interaction] [--e2e ios] after inspecting scope; preserve risk flags. Before final response invoke exactly python3 .flutter-harness/bin/harness.py deliver after acceptance passes. It requests owner publication permission, commits, pushes and verifies one PR. Never merge or publish separately. If interrupted retry deliver on unchanged evidence; preserve the original delivery.json and do not repeat checks. On a structured non-retryable delivery failure report the exact code/stage and required owner action; never regenerate a manifest after commit. Report DONE only on current PASS receipt, otherwise specific BLOCKED/INCOMPLETE. Delivery ends this task; do not edit after it in the same turn.
